当前仓库**没有 Web 后端/前端代码**，因此暂无 SQL 注入、XSS、鉴权绕过等 Web 攻击面可审。主要问题集中在：

1. **容量总数重复计数**（P0）；
2. **跨季分割指标因 RGB/BGR 通道错位而严重偏低**（P0）；
3. **DOTA 训练图像写盘时 R/B 交换，推理依赖“反向错误”对齐**（P0）；

此外还有 8 项评估口径/数据质量问题（P1）和一批健壮性、安全、工程问题（P2）。

## 二、P0：会让结题数字或结论错误

### P0-1 容量总数把同一地块算了两次

**位置**

- `ml/scripts/18_capacity_engine.py:118-142`：把 OSM 多边形追加到 `items`；
- `ml/scripts/18_capacity_engine.py:144-160`：所有 `items` 统一算容量并求和；
- `ml/scripts/18_capacity_engine.py:157`：`capacity_total = sum(...)`；
- `data/capacity/aoi_capacity.csv`、`data/capacity/aoi_capacity_utm.geojson`。

**证据**

脚本没有对分割多边形和 OSM 多边形做匹配/去重，二者覆盖同一批物理地块：

| 重叠对 | 重叠面积 | 占较小者比例 |
|--------|---------:|-------------:|
| `seg_011` ∩ `osm_025` | 15,894.6 m² | **93.6%** |
| `seg_023` ∩ `osm_024` | 1,872.5 m² | **90.7%** |

整体：

- 26 个多边形面积合计 130,880 m²；
- 并集面积 113,113 m²；
- 重叠 17,767 m²，占 **13.58%**；
- 当前 `capacity_total = 4674`；
- 按并集面积、同样 28 m²/车位算，约 **4040**；
- 只信分割：**3456**；OSM 单独：**1218**（几乎全是重复）。

**影响**

- 结题报告/Web 看板的“总容量”不可直接使用；
- `data/capacity/truth_collection_sheet.csv` 的 26 行同时包含 `osm_025` 与 `seg_011`、`osm_024` 与 `seg_023`，真值采集会重复；
- 校准集/测试集若包含重复地块，MAE/MAPE 口径会被污染。

**修复建议**

1. 先做地块匹配：按 IoU 或质心距离，把 OSM 与分割多边形配对；
2. 重叠对只保留一个来源（建议 OSM 边界优先，或直接取并集；在属性里记录 `source` 与 `matched_id`）；
3. 输出 `capacity_total_unique`，同时保留 `capacity_seg` / `capacity_osm` 分来源合计，但**不要**把两者相加作为总数；
4. 重新生成 truth sheet，确保每个物理地块只出现一次；
5. Web 看板展示时按唯一地块渲染，不要叠加两个来源的多边形。

**验收标准**

- GeoJSON 中不存在重叠面积超过较小者 30% 的跨来源要素；
- `capacity_total_unique` 与并集面积/系数一致；
- truth sheet 的 `lot_id` 全局唯一，且每行有 `source`/`matched_id`。

### P0-2 跨季分割命中率 26% 是通道顺序造成的，实际约 65%

**位置**

- `ml/scripts/17_eval_summer.py:57`：rasterio 读出 RGB；
- `ml/scripts/17_eval_summer.py:62`：`seg(arr, ...)` 直接传 RGB；
- `ml/scripts/11_infer_seg_full.py:45-50`：同样直接传 RGB；
- 训练侧：`ml/scripts/06_prep_seg_data.py:107-108`、`ml/scripts/09_prep_seg_manual.py:88-89` 都是 rasterio RGB → `COLOR_RGB2BGR` → `cv2.imwrite`，即训练图像是正确的 BGR；
- 正确示例：`ml/scripts/18_capacity_engine.py:94` 做了 `tile[:, :, ::-1]`。

**证据**

同一分割权重 `runs/segment/parking_seg_night/weights/best.pt`，同一批 23 个夏季 OSM 窗口，`imgsz=1024, conf=0.25`：

| 输入 | 有分割的窗口 | 命中率 | 实例总数 |
|------|-------------:|-------:|---------:|
| RGB（当前 17） | 6/23 | **26.1%** | 7 |
| BGR（正确） | 15/23 | **65.2%** | 25 |
| 原生 512×4 子窗 BGR | 16/23 | **69.6%** | 30 |

冬季 `lot_01` 单窗：RGB 3 个实例，BGR 9 个实例。

`doc/records/imagery-2026-10.md:133` 的“6（26%）”与 `17` 的 RGB 结果完全一致，说明文档数字确实来自这条错误路径。

**影响**

- `doc/records/imagery-2026-10.md:133,138`、`doc/current/assessment.md:23`、`doc/background/onboarding.md:157` 的“跨季泛化 26% vs 27%”“跨季无显著退化”“瓶颈是标注数据规模”结论失效；
- 26% 与 27% 的对照口径（窗口集、脚本、通道）也需要重新核对，不能继续引用；
- 分割模型的真实跨季能力被严重低估。

**修复建议**

1. 在 `11`、`17` 调用分割模型前加：
   ```python
   bgr = np.ascontiguousarray(arr[:, :, ::-1])
   r = seg(bgr, ...)
   ```
2. 重跑 23 个夏季窗口，更新 `doc/records/imagery-2026-10.md`、`doc/current/assessment.md`、`doc/background/onboarding.md`；
3. 在文档中明确“分割模型输入为 BGR，推理前必须转换”；
4. `18` 已经正确，不要改；
5. **不要顺手把 13/19/20 的 DOTA 调用也改成 BGR**，原因见 P0-3。

**验收标准**

- `17_eval_summer.py` 的 `summer_eval.csv` 中 `seg_lots>0` 的窗口数从 6 变为约 15；
- 文档中的 26% 被替换为修复后重跑的数字，并注明权重、窗口集、`imgsz`、`conf`；
- 新增一个“RGB/BGR 通道约定”测试或注释。

### P0-3 DOTA 训练图像写盘时 R/B 交换，推理靠“反向错误”对齐

**位置**

- `ml/scripts/04_dota_to_yolo_obb.py:159-160`：
  ```python
  cv2.imwrite(
      str(out / "images" / split / f"{fname}.png"),
      cv2.cvtColor(tile_img, cv2.COLOR_BGR2RGB),
  )
  ```
  `tile_img` 来自 `cv2.imdecode(..., IMREAD_COLOR)`，本身是 BGR；再转成 RGB 后交给 `cv2.imwrite`（按 BGR 解释），等于把 R/B 交换后落盘。

**证据**

最小复现：输入 BGR=(10,20,30)（即真实 RGB=(30,20,10)），走上述写盘路径后，用 PIL 读回：

```
期望存储 RGB=(30,20,10)
实际存储 RGB=(10,20,30)
```

模型行为也一致：

| 模型 | RGB 输入 | BGR 输入 |
|------|---------:|---------:|
| DOTA `lot_01` | 323 | 138 |
| DOTA 三个冬季窗口合计 | **433**（323/47/63） | **212**（138/29/45） |
| GE v2 `lot_01` | 6 | 7 |
| GE v2 三个冬季窗口合计 | **26**（6/9/11） | **19**（7/3/9） |

`doc/records/detection-2026-10.md` 里记录的 DOTA 冬季 433（323/47/63）正是 **RGB 路径**的结果。

**为什么会“看起来正常”**

- Ultralytics 的 numpy 输入按 **BGR** 解释；
- DOTA 训练图像被交换过 R/B，模型学到的就是交换后的颜色；
- `13/19/20` 把 rasterio 的 RGB 直接传入，第二次交换把颜色换了回来，于是与训练一致；
- 任何新脚本如果按“正确 BGR”传参给 DOTA 模型，就会出现 323 → 138 的骤降。

**影响**

- 这是一个隐式耦合，后续成员/脚本很容易踩坑；
- 不能用“BGR 更正确”为理由直接改 13/19/20，否则会无意中改变所有已记录的 DOTA 数字；
- 若重训 DOTA，必须同时改所有推理脚本，否则会得到第三套结果。

**关于“GE 微调对 JL1 负迁移”结论**

已复核：GE 模型训练时使用正确 BGR，用 BGR 重跑三个冬季窗口为 7/3/9（合计 19），RGB 为 6/9/11（合计 26），**两种都远低于 DOTA 的 433**。因此负迁移结论仍然成立，域分离策略不需要推翻。

**修复建议**

短期（不重训）：

1. 在 `04` 文件头、`13/19/20` 文件头明确写“当前 DOTA 权重期望交换 R/B 的输入”；
2. 增加一个 `to_dota_input(arr_rgb)` 辅助函数，内部做 `arr_rgb[:, :, ::-1]`，避免成员自行猜测；
3. 不要在未重训前改 13/19/20 的 DOTA 推理通道。

中期（重训）：

1. 把 `04` 改成直接 `cv2.imwrite(..., tile_img)`（BGR）；
2. 重训 DOTA；
3. 所有检测推理统一 BGR；
4. 增加 1 像素颜色测试，断言写盘/读回通道一致。

**验收标准**

- 旧权重：文档明确标注“DOTA 输入需交换通道”；
- 新权重：`04` 写盘不再 `BGR2RGB`，13/19/20 全部使用 BGR，DOTA 指标重新记录；
- 不再存在“训练和推理各错一次”的隐式依赖。

### P0-4 JL1 预标注窗口大量重叠

**位置**

- `ml/scripts/20_preannot_jl1.py:56-64`：按 OSM 元素质心逐个裁 1024 窗口；
- 没有中心距离、IoU 或 OSM ID 去重。

**证据**

从 `data/jl1_annot/<scene>/preannot_raw/` 的文件名还原 OSM 索引和窗口位置：

| 场景 | 窗口数 | 重叠对数 | 典型重叠 |
|------|-------:|---------:|----------|
| `summer` | 12 | 6 | 75/76 58.3%；75/77 63.1%；76/77 34.2% |
| `summer_june_south` | 12 | 8 | 0/1 74.6%；10/11 83.8%；34/36 80.6% |

合计 24 个窗口中至少 14 对存在重叠，部分超过 80%。

**影响**

- 标注组（当前关键路径）会把同一片车场、同一批车标两三遍；
- 未来 JL1 微调若按窗口随机切 train/val，重叠窗口会同时出现在两边，造成严重泄漏；
- 预标注数量“24 窗口”看起来充足，实际独立场景数明显更少。

**修复建议**

1. 生成窗口时做贪心去重：按质心距离 ≥1024 px，或窗口 IoU <0.3；
2. 大停车场允许保留多个窗口，但总重叠控制在 30% 以下；
3. 输出 manifest：`scene, tif, col, row, osm_id, n_boxes, mean_score`；
4. 未来切 JL1 训练/验证集时按场景/地理区域划分，不要按窗口随机划分；
5. 若已开始标注，先按 manifest 合并重叠窗口，避免继续重复劳动。

**验收标准**

- 同一场景内任意两个窗口重叠面积 <30%；
- 每个窗口能通过 manifest 追溯到 TIF、col/row、OSM ID；
- 预标注数量按“独立窗口”统计，而不是按生成次数统计。

### P0-5 GE 切片漏掉每张图约 18% 的标注框

**位置**

- `ml/scripts/15_ge_tile_obb.py:55-56`：
  ```python
  for y0 in range(0, H - TILE + 1, STRIDE):
      for x0 in range(0, W - TILE + 1, STRIDE):
  ```
  只生成完整切片，没有补 `H-TILE` / `W-TILE` 的最后一个窗口。

**证据**

当前 25 张 GE 图统一为 **4800×3134**，`TILE=1024, OVERLAP=200, STRIDE=824`：

- 横向起点：0, 824, 1648, 2472, 3296 → 最后覆盖到 4320，右侧 480 px 未切；
- 纵向起点：0, 824, 1648 → 最后覆盖到 2672，底部 462 px 未切；
- 覆盖区域 4320×2672 = **76.7%** 面积；
- 原始标注 2139 框中，**386 框（18.0%）**落在未覆盖条带；
- 12/12 张图都受影响；
- 训练集中 **377 个框**不完全落在任何生成的切片内。

**影响**

- GE 微调/留出评估都没有覆盖约 18% 的标注；
- 边缘车辆永远学不到，val 指标也不代表整张图；
- 与 P1-1 叠加：数据集既没有背景切片，又漏掉边缘目标。

**修复建议**

复用 `18_capacity_engine.py:52-58` 的 `tile_positions()`：

```python
def tile_positions(size, tile, stride):
    if size <= tile:
        return [0]
    pos = list(range(0, size - tile, stride))
    if pos[-1] != size - tile:
        pos.append(size - tile)
    return pos
```

然后重跑 `15_ge_tile_obb.py` → `16_finetune_ge_obb.py` → `19/20` 的 GE 评估。

**验收标准**

- 4800×3134 图生成 24 个候选切片（而不是 15 个）；
- 每个标注框至少完整落在 1 个切片内（除刻意丢弃的极小框）；
- 重新统计 train/val 切片数与框数，并在 `doc/records/detection-2026-10.md` 更新。

## 六、已确认正常的部分

- **OBB 读取**：当前脚本使用 `res.obb`，没有 `res.boxes` 误用；`13` 的修正说明也明确记录了这一点。
- **OBB 指标 API**：`19` 的 `m.box` 在 `ultralytics 8.4.140` 的 `OBBMetrics` 上可用，已实际跑通。
